# Frontend rendering

The front end has two jobs: PHP decides which icon belongs to a post at request time, and JavaScript places that icon beside the title element a reader actually sees after the theme lays out the page.

## Resolution and data flow

1. `Title_Renderer` registers a `the_title` filter, but returns the title unchanged. On eligible visible post-title reads it records the resolved icon entry by post id.
2. Eligibility requires the global plugin switch, an enabled post type, an enabled display location (post pages, homepage, archives or search results), an enabled post timeline, a valid active stage, and an asset still present in the library. Every front-end context resolves to one of those four locations: search results have a switch of their own, and any other listing — a 404 whose template prints posts, for instance — follows the **Archives and categories** choice instead of resolving nothing.
3. `Settings::anchor_for()` selects the saved per-post anchor, fixed site anchor, or publish-date fallback.
4. `Decay::resolve()` computes stage, elapsed/remaining time, and end time. Zero-duration stages are skipped. A future anchor yields stage one without a negative elapsed time.
5. At the bottom of the page, PHP queues the frontend bundle if an icon was resolved or enabled homepage widgets may need title-link decoration, and inlines the compact icon list in `window.titleSparksFrontendData`.
6. `frontendTitleDom.js` finds the matching visible title in the completed document, creates a hardened icon element, inserts it inside that title (or beside a card link's text box when the same link also carries the thumbnail), and positions it using shared editor/frontend measurement functions. The icon is always measured against the title's words, never the card around them.

This separation is deliberate: WordPress’s `the_title` filter also runs for attributes, metadata, feeds, breadcrumbs, and secondary title reads. Changing the title string to markup breaks themes and can place an icon in the wrong title. TitleSparks records data during the filter but never injects HTML into the returned title.

## Which title is selected

The finder checks candidate headings and known title classes, excludes site branding, hidden regions, comments and other non-title regions, and compares normalized title text and post permalinks. Every visible copy of an eligible post's title gets the icon, on every page the display settings cover: a post's own page decorates the heading a reader is looking at first and then each further place that page prints the same title (a related-stories rail, a “More posts” query loop, a sidebar's latest-posts list), and a homepage, archive or search results listing decorates every title-and-permalink-matched occurrence, including a featured carousel and a second list card. A title is compared after folding theme typography *and* the HTML entities the server's copy carries — WordPress hands a bare `&` out as `&#038;` while the theme's page shows the decoded `&`, and a title containing an ampersand used to match nothing at all. What stays bare: carousel clones, thumbnails, a paragraph that merely quotes the headline, comments, breadcrumbs, navigation, site menus, hidden regions, and any widget or theme area switched off in Settings. A previous/next post link is an ordinary title occurrence: its title gets the icon, while the thumbnail beside it does not, and it is sized the way the post it names is sized rather than the way the page it appears on is — the link keeps the post's own id, so the browser places it from that post's entry, with that post's sizing mode, title-size table and nudge, exactly as the title is drawn on its own page. An occurrence that identifies itself — its own heading, a title class, or a link whose whole text is that post's title — is kept even when another occurrence on the page is a heading. The block-level preference exists to refuse a body element that merely holds the same words, and answering it for the whole page at once dropped a post page's previous/next links, which are bare inline links inside a `nav`, whenever a listing card elsewhere on the page matched the same title. Verified by giving one neighbour a distinctive table (16px title, 44px icon) and reloading a post page: both adjacent titles followed their own post's table, and the untouched neighbour stayed at its own size. The finder logic is pure where possible and covered by `frontendTitleDom.test.js` with representative theme markup, and the adjacent links of a real post page are covered end to end by `tests/integration/adjacent-post-icons.cjs`, which fails when either of them is left bare.

The settings screen’s **Show icons on** options independently enable post pages, the homepage, archive/category pages, and search results. A homepage or archive option also covers featured sections and other secondary theme queries on that page; WordPress does not provide a standard way to identify a theme’s “featured” section separately. The server therefore records eligible post titles read on the page, including in secondary queries, while the browser still requires an exact title/permalink match before inserting an icon. A title repeated in a sidebar can also match on an enabled listing page. Static front pages are treated as homepage contexts for both their own queried page title and eligible post titles from their secondary loops when homepage display is enabled.

The **Theme areas and widgets** list combines areas found by the deep scan with active WordPress widgets, each with an independent setting. For the NewsOnline/NewsMash theme it includes **Main Featured**, **Featured Posts**, **Latest Post**, **Other Story**, and **Popular Categories**; the labels follow the theme’s visible headings or component names. On any theme, the scan reads every block template the active theme (or a plugin) registers, every template part those templates are built from, the stored content of a static front page, and the most recent content of every public post type — posts, pages, products and the rest. A classic theme keeps its single-post and single-page layouts in PHP templates that cannot be read, but whatever the author put in the post or page itself renders there, and different items hold different blocks; reading several per type is what finds the related-posts rail, the query loop and the “more stories” list that only some posts use. Each block that can hold post titles becomes a section, using the block’s anchor, author class, or generated `wp-block-*` class as its selector, and blocks with no distinguishing class share one section. A synced pattern is walked into rather than listed as a section of its own: a `core/block` reference renders whatever the pattern holds with no wrapper, so its own blocks become the sections, read from the pattern at scan time and guarded against a pattern that includes itself. The scan records the page contexts each source renders in (`home`, `singular`, `archive`, `search`, or `all` for a template part) and names the source in the settings, so a section found on a single-post template says so instead of looking like a homepage control. Other themes can register their own areas with the `titlesparks_homepage_sections` filter and provide each section’s DOM selectors; a section registered without contexts applies on every page. Active widgets are listed separately and named with the sidebar areas they appear in; a block widget is scanned through every nested block and named from its visible heading, its registered block title, or the block name in words, so it reads **Latest Posts** or **Query Loop** rather than the generic **Block** label. A block widget holding no block markup and no heading — text pasted in as HTML — has nothing to read, so it keeps that generic widget name, and any name two widgets share is suffixed with the instance ID (`Search (block-3)`) since the row is otherwise indistinguishable from its twin. Each widget also says which pages its sidebar renders on, read from the theme’s own PHP files for `dynamic_sidebar()` and `is_active_sidebar()` calls: a sidebar printed only by a single-post template says so, and the widget’s switch follows those pages. A theme that passes a variable, or builds its sidebars some other way, leaves the plugin nothing to read, so those widgets keep **Every page** rather than being guessed at. Both reads are cached — the template scan and the sidebar map — and are thrown away when a post is saved or deleted, when the theme changes and by **Deep scan**, so an edit to a post is reflected on the next request instead of waiting for a timeout. **Deep scan** re-reads all sources without reloading the dashboard. Unset choices default on. Each checkbox gates only title matches inside its section on the pages that section appears on; disabling one theme area does not suppress icons in another area or in widgets, and a single-page section no longer needs the homepage switch to be on. A widget's own choice applies wherever the widget renders — a post page, the homepage, an archive or search results — because a sidebar is not tied to a page type. The browser still decorates every visible title occurrence matching the post title and permalink, while skipping hidden carousel clones and comments; on a post's own page, only a copy inside a switched-off section is left bare, and every copy outside every section keeps its icon.

If a theme has a title wrapper that does not match existing selectors or semantics, first inspect its rendered DOM and extend the finder with a regression fixture/test. Do not broaden a selector without checking site branding, sidebars, archive cards, comment headings, and repeated title text.

## Position, dimensions, and offsets

- The picker offers two positions, **Left of title** and **Right of title**; vertical placement is done with the offset fields, which move the icon freely in both directions. A side icon is measured against the words of the line it is anchored to, not against the whole text block: a right icon sits one gap past that line's last character and a left icon one gap before its first, so an icon on the first line hugs the first line's words. Anchoring to the widest line instead left a right icon on a wrapped title 148px beyond the words it labelled (and, with `last_line`, 208px away and past the title on a phone). `icon_anchor = last_line` uses the bottom line's own edges; the default `first_line` uses the first line's, and `block` keeps the whole text box for a site that wants the older alignment. The vertical anchor is stable either way, so a title that wraps to two or three lines keeps the icon on the line the author gave it. A timeline saved by an older version with a vertical or corner position still renders there, and its editor shows the saved value as a disabled legacy choice, until a side is picked.
- `editorTitleDom.js` is shared by the editor canvas and frontend so both use the same geometry and placement logic.
- The default gap is font-relative (`0.15em`) at every title size, with a 6px fallback only when the font size cannot be measured. There is deliberately no pixel floor: a floor is not a safety net for the fraction but a second rule for small titles (4px beside a 15px widget title is 27% of the letters where the fraction asks for 15%), which spaced the small copies on a page differently from the main title they were tuned beside. Measured live on the reference site, the gap now runs 2.25px beside a 15px widget title, 3.6px beside a 24px card title and 4.8px in the 32px canvas — one ratio throughout.
- X/Y offsets are author-entered screen deltas (positive right/down, negative left/up), clamped to ±100 and scaled relative to a 32px editor title reference so their relation to the text is consistent at frontend font sizes. The scale is the title's own `font-size ÷ 32`, exactly, so a nudge covers the same share of the same letters at every size and a card copy looks like the post's own page — a 15px widget title gets 0.47x of the authored number, not more. Only the top is held, inside `OFFSET_SCALE_MAX` (1.4), where a 60px headline would otherwise have grown the nudge to 1.88x of what the author typed and cleared a whole line. A title-following icon adds a second limit on the same scale: the nudge follows whichever is smaller, the title's growth or the icon's own, so a title whose bands stop growing the icon (the same 45px beside a 40px title and a 32px one, where the text asks for 1.25x) no longer moves the nudge away from the text it stopped growing with. The icon's growth is measured from the size the same bands draw at the 32px canvas, not from the page's own main title, because the canvas is where the table was written: an icon at the same width beside a 40px main title keeps its nudge as it is — a 60px title that the bands hold at that width draws the icon at the same size, so the nudge holds too — and `offsetScale.test.js` pins that case. A fixed-size icon has no bands to reach and keeps following the title, which is what the letter-covering nudge is for. Both axes move freely in either direction on every position, so an offset may deliberately bring the icon over the title text. They are measured from the title's **first line** by default: the range's per-line client rects give that line's height, so a title that wraps to two or three lines keeps its icon exactly where the author put it, in the editor canvas and on the front end, which apply one shared placement rule. The `icon_anchor` setting can anchor the icon to the **last line** instead, using that line's height and its offset from the top of the text box, or restore the older `block` rule, which centres the icon on every line together and so moves it down as the title grows. A copy of a post's title gets the post's offsets on the page exactly as the post's own title does: a card's icon is taken out of the flow and placed by the same rule, with no clearance held back. `ICON_MIN_CLEARANCE` (2px) survives only for icons still drawn in text flow (`placeInlineIcon`), which this version no longer writes to the page. So a post whose icon was nudged onto its words shows that same overlap in a widget, a listing card and its own page alike, scaled by the title's size. Both the anchor and the space are also per-post answers, stored beside the timeline: a post that picks its own line or its own space overrides the site setting for that post's icon wherever it is drawn, and an empty answer keeps following the site. `icon_spacing = flush` drops the gap to zero and with it the small-icon centring, so the icon's own edge — not a middle held half a box out — is what touches the last character. The measured edge is the last (or first) non-space character of the line: Chrome gives the space that ends a wrapped line a rect of its own, and measuring to that rect left a flush icon one space away from the words it was meant to touch (11px beside a 40px title). Spaces typed before or after the title are dropped the same way, so no title can push its own icon out; the site can make that its own default in Settings, and a post that never chose keeps up with it.
- Side placements keep the icon's middle on the title's line (`top` plus `translateY(-50%)`) and keep it clear of the words: up to a 20px box (`ICON_ANCHOR_SIZE`) the centre sits one gap plus half that box from the text and resizing narrows the icon about that point; wider icons are held at the gap and grow away from the title. Measured live, anchoring a 54px icon by its middle alone covered 11.6px of the title in the canvas and 15.2px on the page, which is why the gap wins above the anchor size. The canvas, sidebar preview and page — widget and Posts Slider titles included — all use `placeIcon`, so a card in a slider is placed exactly like the post's own title. An icon nudged past the edge of the page is moved back only as far as the page's edge rather than to the title's own edge, so a narrow canvas that leaves less gutter than the nudge needs keeps the overlap the post's page shows. The editor also keeps asking the canvas for the icon while it boots: WordPress can replace the title's wrapper after the canvas component has attached its observers, and without that retry the live icon appeared only when a later resize or edit happened to ask for it again.
- Stage-specific icon size wins, then asset size, then `20px`. A stage set to **Advanced (custom sizes)** is sized from its title-size bands instead: `advancedIconWidth()` reads each band as the icon size at one title size and holds that size from the band's own title size up to the next one, so a 15px title under bands of 12/10 and 16/12 draws 10px, and 32/32 with 40/45 draws 32px beside every title from 32px to 39.99px and 45px from 40px up. Outside the table the nearest band holds, so a title larger than every band uses the last one. Nothing is interpolated: an icon takes a size the author typed, and a heading that crosses a row changes the icon once, at a title size the table names, rather than drifting through numbers the table does not hold. Each entry carries the bands its stage is drawn from — the stage's own table, or the site's when it has none — so two posts in one list can be sized from different tables, and a stage set to a fixed size is never resized by them. The drawn width still feeds the nudge's growth so the offset stops where the icon stops.
- Widget titles follow the post title's position, size rule and offsets unless the widget instance stores its own valid position; no hardcoded widget default is applied. This keeps an “Express Posts List” widget icon on the same side and nudge as a post icon in the same page.
- Widget icons are positioned absolutely like a post icon (`placeIcon`, with the card as the boundary), so the old in-flow `titlesparks-icon--inline` class is removed before anything is measured: its `margin-left` would otherwise shift the icon by a second gap on top of the measured one (measured 6px where the rule says 4px). Legacy markup from an older cache is stripped the same way.
- When the selected title sits inside a card link that also wraps the thumbnail, the icon is inserted into that link beside the card's text box, not inside the text span. Themes write rules such as `.nav-content span { padding-left: 2rem }` and `.nav-content img { margin-left: 2rem }` for their own text and picture; inside the span those collapsed this plugin's icon to zero width. The icon stays clickable in the same link and is still measured against the title span, so it lands with the words rather than the picture. The words are found in the link's own markup instead of inferred from what the link contains: a previous/next link can hold its title in a block-level box, or gain its thumbnail after the page has rendered, and a block-level child reports a rect as wide as the link. Measuring that box put the icon at the link's edge — up to a hundred pixels from the words, with the space it belonged in left empty — so `insertIcon` records the innermost element that carries the whole title and the placement measures that. `frontendTitleDom.test.js` pins both the link with no thumbnail and the one whose thumbnail arrives later.
- An icon the pass already placed is never mistaken for the card's picture. Counting it as media made the answer depend on where the icon was: with the icon inside the card's link, both the link and the heading around it "held media", so the next pass picked the heading, the one after that picked the link again, and the icon moved between the two every pass — measured on an archive, one pixel away from the last place each time, for as long as the page stayed open. `holdsMedia` ignores pictures inside `[data-titlesparks-icon]`, and every answer built on it — the words' node, the finder's scoring, the card-link test and the widget title — is therefore the same whichever element currently holds the icon. `frontendTitleDom.test.js` decorates the same card three times and requires the page to be unchanged, and the live check below fails an icon whose host element changes.
- A title's alignment is the theme's, and the plugin never writes `text-align` on a title it decorates. A previous/next block may right-align its title so the lines meet the thumbnail beside it, leaving the left end of every line empty: measured on the reference site, the theme gives that span a fixed width with `padding-left` and `text-align: end`, and its two lines end on the same edge, so the shorter first line starts further right. That is the theme's arrangement — the plugin's icon is absolutely positioned, changes no rect (removing it leaves every measurement identical), and the space is there with the script blocked. Leaving it alone is the default; starting the words would move them, which is the one thing a decorated title must not do unasked.
- A widget icon is drawn inside a card, which may clip its edges. **Fit icons inside tight cards** is one on/off switch: `keep` (off, the default) draws the icon exactly as the author placed it and leaves the card edge to the theme; `shrink` (on) draws the icon at the width the card's padding leaves beside the words, down to `TIGHT_FIT_MIN_ICON` (8px), and leaves it alone when even that will not fit. It acts only where the boundary's overflow is `hidden`, `clip`, `scroll` or `auto`: a card that lets the icon show has nothing to fit, so the author's placement stands there — measured on a recent posts item, the icon sat in the theme's own page padding while the title was indented by the width of the icon for no reason. The title is never indented and never wraps a line earlier; the icon is the only thing that changes size. A fitted width survives the re-measure that follows, so a title-following icon is not put back at its band size and shrunk again on the next pass. The card is the nearest ancestor that clips or owns horizontal padding, not simply the nearest list item. `wrap` was this answer's older name, still understood by the placement for a page cached from that version, and `hide` is retired and sanitized to `keep`. Placement never draws the icon over the words, and it re-measures after layout changes so the icon stays with its line.
- A stage can mirror its icon with `flip`. The server adds `titlesparks-icon--flipped` to the markup and the front-end entry carries `flip` for icons the script inserts; the editor canvas adds `titlesparks-title-icon--flipped`. In both surfaces the mirror is `transform: scaleX(-1)` on the image, not the icon element, so it cannot disturb the placement transform that centres the icon on its line. The choice belongs to the stage, so the library asset and the other stages are unchanged.
- The icon's stacking order is the site's `icon_z_index` setting, written as an inline `z-index` by the same placement function in the canvas and on the page. It is applied on every pass rather than only when the node is built, so changing the setting moves an icon already on the title. `0` — the default, and what an unset site resolves to — clears the inline value instead of writing one, leaving the page's normal order untouched. The number is clamped to what CSS accepts; a theme can still stack above it by choosing a higher number of its own.
- Icon presentation belongs to the theme. `assets/css/title-icons.css` sizes the image, lays it out as a block so the icon's box is the picture rather than a line of text, and supplies the in-flow gap; it declares no `!important` rules and does not reset colours, borders, padding, background, shadow or visibility. The block rule is deliberately more specific than a theme's broad `... img { display: none }` thumbnail rule, which hid the icon in a small-screen previous/next block; a theme can still override it. The same rule repeats the size for the same reason: the reference theme styles its adjacent-post pictures with `:is(.nav-previous, .nav-next) img { width: 80px; height: 80px; object-fit: cover }`, and the theme's own `img { max-width: 100% }` capped that width against the icon's placed box while the height was left free, so an icon the bands drew at 20px rendered 20x80 — cropped, reading as if the size mode were ignored. The width the placement chose now decides the box and the height follows from the picture. `iconBox.test.js` guards this, and the live check below fails any icon whose drawing does not keep its picture's shape.
- Icons have escaped URLs/alt text, a data marker for post id, and `loading="lazy"` / `decoding="async"` in editor preview markup. The frontend script avoids emitting an icon twice for the same post.

## Loading behavior

The small stylesheet is enqueued when the site-wide feature is enabled. The JavaScript bundle is enqueued late only when there are eligible page-title entries, enabled widgets, or theme sections that may need placement on the page being served. Bundle dependencies/version are read from each build’s `.asset.php` manifest by the shared PHP asset trait.

The frontend placement pass handles layout changes such as web fonts and responsive reflow. Keep the plugin additive: avoid changing title text, broad global styles, or theme layout beyond the positioned icon and its necessary title positioning context.
